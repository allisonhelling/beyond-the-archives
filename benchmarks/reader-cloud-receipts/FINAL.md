# Final Hybrid Reader Cloud Protocol

## Implementation

The forward migration [20261121000100_reader_hybrid_sync.sql](../../supabase/migrations/20261121000100_reader_hybrid_sync.sql) replaces the original receipt layout in the existing private table. It stores the owner and operation UUID, accepted key, revision and generation, the immutable request digest, and an optional accepted value. The RPC keeps one accepted result contract. It hashes PostgreSQL JSONB text for the original key, value, base revision, and generation under the per-owner operation identity. It checks the digest on replay and stores a fallback only when the accepted text differs from the submitted text. This includes values normalized by shared reader and organizer state. JSONB makes object member order canonical. The comparison deliberately preserves PostgreSQL's JSONB text for numeric representations.

The migration removes the old signature and rejects populated legacy data. The reader uses a single atomic IndexedDB flight claim across tabs, even when Web Locks are missing. Both the reader and organizer persist immutable requests for ambiguous retries. The existing polling cadence and full-snapshot fallback remain in use.

Deleting a book advances its epoch, erases its active state and irreconstructible accepted payloads, and retires its Storage path. The immutable generation is part of every EPUB object name. Storage permits owner removal only for retired paths, and the RPC checks that the former object is gone before restoring. It recognizes stale writes even when a recreated field has the same revision number. Calibre pins a generation to each transfer reservation and can stage the prospective next original. A retired delivery retains its ID with its metadata cleared. A withheld, historical deletion reply remains idempotent and cannot authorize removing the new file.

Explicit deletion overrides retention of irreconstructible accepted values. For those redacted operations, the ledger retains the immutable request binding and returns a stale outcome. Pass-through replies need no stored personal payload and can still replay the authenticated caller's exact input. This avoids retaining deleted book content, fields, or Calibre metadata for replay. Logical removal and physical PostgreSQL space reclamation are separate.

## Actual Schema Benchmark

`node benchmarks/reader-cloud-receipts/final.mjs 3` used the complete migration chain and the actual RPC on PostgreSQL 17.5 through PGlite. It ran 23,817 accepted synthetic workload operations per trial, plus 48 setup operations across 12 owners to exercise real fallback normalization. The workload reuses the previous synthetic payloads. Generated scalar deletion entries become non-lifecycle measurements so the main batch remains a fixed-size comparison. Separate cleanup measures one actual lifecycle transition with a normalization fallback to redact. Probes store original bases and reply hashes in a temporary table, and 512 replays verify historical equality after intervening writes. Insert timings include the active-value upsert, temporary probe, digest, receipt and trigger work. They are distinct from the prototype's receipt-only timings.

The [earlier full JSONB relation](RESULTS.md) used 105.19 MiB for 23,817 receipts. The implemented schema measured about **94% lower physical receipt storage** in the low-fallback synthetic cohort, even with 48 extra rows. Applying that ratio to the supplied 101 MB receipt footprint gives about 6 MB in equivalent receipts after a clean reset and comparable new workload. The prior 5–50% fallback scenarios found savings of about 48–90%. Neither comparison predicts the live fallback rate or project disk size. WAL includes active-value changes and is an absolute measurement in the embedded benchmark. The code still returns the accepted value and adds the generation field. At the same polling rate, receipt compaction alone does not lower response bytes.

### Native PostgreSQL Cross-Check

A single trial on PostgreSQL **17.11 aarch64**, using a disposable, network-disabled container with PGLZ and `fsync=on`, reproduced **6,578,176 bytes** of receipt storage and **12 fallback values**. The bulk and repeated-write phases took 19.00 s and 0.48 s. The four 512-operation replay batches took 160–341 ms and generated zero WAL. The retirement took 57 ms. Total WAL for the main write cohort was 120.31 MB. Separate native sessions submitted the same operation simultaneously and returned identical results with a single ledger row at revision one. The native trial used the benchmark SQL only and did not run the Supabase Storage HTTP service.

## Validation

- The full embedded database, Organizer offline unit, and Calibre handler run passed **474 tests**. After the final migration guard and queue refinements, the focused database and unit suites passed again. The independent Reader unit suite passed **109 tests**.
- The focused Reader Playwright run passed **18 tests**. It covers immutable retries before and after commit, two tabs without Web Locks, rebase, scheduler recovery, stale deletion replay, Calibre publication, and reimport. The Organizer offline browser suite passed **two tests**. The Calibre companion's Python suite passed **ten tests**.
- A full Reader browser sweep reported 106 passes and nine failures. Eight failures reproduced on the pre-change revision in an isolated checkout. The remaining publication-color assertion passed when rerun alone. This run is not a clean full-suite result.
- Native PostgreSQL accepted one receipt for simultaneous duplicate requests. A concurrent original upload addressed to a retired generation was rejected. The restored generation's original survived a historical deletion replay and an old-session deletion attempt against its active path.
- Repository lint, root TypeScript, both production-preview builds, and whitespace checks passed. The embedded and native checks exercise PostgreSQL operation ordering and Storage metadata authorization. Browser tests mock the Storage HTTP service. Keep an authorized live Storage and Calibre smoke check in the cutover gate.
