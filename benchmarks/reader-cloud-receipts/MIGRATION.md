# Historical Receipt Migration Proposal

The final pre-release decision superseded this mixed-client proposal. See the [final benchmark](FINAL.md) and [clean reset procedure](../../reader/docs/CLOUD_PROTOCOL_RESET.md).

Keep the current RPC and legacy receipt table during a mixed-client rollout. The preferred experiment is a versioned hybrid for **new** operations, with a full accepted-payload fallback where the frozen request cannot reproduce the accepted value exactly. The [benchmark](RESULTS.md) does not justify rewriting legacy receipts into a request-dependent format.

## Phase 1 — Verify the Contract and Workload

1. Benchmark the measured candidates on native PostgreSQL with production-like page, compression, durability, concurrency, and payload-size distributions. Measure normalized versus pass-through accepted values and retry rates in aggregate. Measure the fallback share **of bytes** as well as rows.
2. Define an immutable operation identity across RPC versions. Decide how the legacy and versioned endpoints reject or route a UUID previously accepted on the other endpoint. Do not allow separate ledgers to accept the same account/ID twice. Use one owner-scoped transaction lock and a single identity constraint or transactional routing check shared by both endpoints.
3. Define a book generation across deletion and reimport, including older devices that missed the tombstone. Separate a historical operation acknowledgement from current permission to remove a file. A client-side marker comparison alone leaves a race between the check and a Storage call. Evaluate generation-qualified object identity or server-orchestrated, generation-conditional removal. Keep the Auth, owner, and Storage access checks intact. Test the original-hash reimport flow under concurrent deletion before a rollout.
4. Decide whether the versioned endpoint returns a compact acknowledgement or reconstructs a full response from an exact bound request. The former can reduce mutation response bytes and keeps replay independent of the current value. The latter preserves the familiar response shape for valid versioned callers. The acceptable binding must be explicit about canonicalization and the organizer's legacy refresh of the request base.

## Phase 2 — Add and Validate the Versioned Path

1. Add a private, owner-scoped v2 ledger and versioned RPC. Store the accepted revision and a versioned outcome. Store an accepted value whenever exact pass-through is unproven. Read and record operation identity, apply the mutation, and record the outcome atomically. Preserve current conflict reporting, normalization, and deletion ordering. Keep authenticated callers behind checked RPCs and use the existing Auth-user cascade. Restrict direct ledger access and verify grants and forced RLS.
2. Deploy the server first. Make version selection durable alongside the IndexedDB flight and any organizer marking in flight. A pre-upgrade flight keeps the v1 endpoint and UUID. If a response is lost, never resubmit the same operation on a different protocol merely because the first endpoint timed out. Make upgrade and rollback tests include a device that was offline throughout deployment.
3. Verify EPUB deletion clears accepted payloads for the account and book in every representation, including legacy, v2, and any backfill or compatibility table. Design generation fences or minimal operation identities to block stale replays without preserving private deleted payloads. Test concurrent deletes, authorizations, lost responses, and organizer-triggered writes.
4. Exercise mixed releases in staging. Assert exact v1 replay after an intervening revision, correct v2 rebasing, normalized responses, owner isolation, no double application on cross-version races, and safe file removal across restore. Check PostgreSQL CPU, write throughput, table growth and API response bytes separately.

## Phase 3 — Legacy Handling and Physical Reclamation

1. Leave existing exact results in v1 by default. The stored result does not record the original request or normalization. Value equality with the current row cannot prove future replies or changed-argument legacy calls can be reconstructed. Existing v1 devices may return indefinitely with a committed operation whose result they never received.
2. If a native benchmark identifies worthwhile **lossless** v1 repacking, take and restore an isolated reader backup first. Create the replacement additively, capture new writes and book purges transactionally, and copy by stable owner/UUID batches. Coordinate backfill with purge using the same account lock or a deletion fence. Never let an interrupted backfill resurrect deleted payloads. Validate row counts, owner/UUID coverage, and exact replay text before activating the replacement. Keep a synchronized rollback path until cutover audit and retention requirements are satisfied.
3. Budget concurrent old and new relations, intermediate indexes, TOAST, backfill WAL, and backup overhead before rollout. For an online dual-write window, estimate both versions' peak footprint under active writes. Repack or replace the relation only after parity verification and a rehearsed rollback. Ordinary vacuum can make pages reusable. File size can stay flat or increase after maintenance, as this benchmark shows. Reclaim space against an explicit physical measurement target and plan for rewrite locks and temporary disk use. [PostgreSQL Vacuuming](https://www.postgresql.org/docs/17/routine-vacuuming.html)
4. Once v2 is deployed, pause rollout by halting new v2 operations while preserving its replay endpoint and existing outcomes. A destructive schema rollback would strand v2 flights. A legacy expiration policy remains a separate project. An old UUID can be rejected or forgotten only under a protocol that prevents reapplication and lets a device recover its pending intent.
