## Canonical Tag Suggestions

Characters, Relationships and Additional Tags suggestions show verified **Standard Tags** first, followed by **Other / Unverified Tags**, separated by a divider. Verified synonyms resolve to a single canonical suggestion and never appear as separate suggestions. Suggestions are deduplicated with the shared case/accent-insensitive normalization. A canonical name can appear even when saved fics use only its synonyms. Selecting that name includes exact, AO3-verified synonyms; related tags, subtags and similarly worded names are not treated as aliases. Original fic tags remain unchanged. Partial searches and unverified tag names keep the existing substring matching. Personal tags are independent. Relationship suggestions still require text on both sides of `&` or `/`.

Tiles and suggestion fields share one paginated account-scoped cache read per session, rather than restricting cached evidence to the first eight lookup candidates. Already-verified tags outside those candidates are classified immediately. Verification failures display a message in the open suggestion field; they do not classify unknown tags as canonical. While a suggestion field is open, the `tag-resolution` Edge Function checks up to eight relevant names, resolving at most one missing or stale profile per call. It reads AO3's explicit canonical/synonym profile sections, verifies name and category, and uses the existing bounded retrieval and global pacing/pause gate. Low-priority lookups yield to direct metadata imports. Known mappings refresh after 30 days; failed/unverifiable observations remain unverified, retry no sooner than ten minutes, and never overwrite previously verified evidence with a guess. AO3 outages do not block filtering or page navigation. Account caches are isolated and cannot be written by browser clients.

Library, Currently Reading, series searches, automatic collections and collection counts share the same matching rules. Filtered page queries prepare the verified-name lookup once and use JSON key membership during per-fic matching; unfiltered pages skip it. Only affected cached results are invalidated when new evidence arrives. The derived tag cache is not part of personal-library backups and can be rebuilt.

Apply `20261026000700_canonical_tag_suggestions.sql`, deploy the `tag-resolution` Edge Function (`npx supabase functions deploy tag-resolution`), then deploy the website. Local builds do not publish these changes. Until the resolver is available, unverified names stay in the second group and saved-tag searches continue working.

Shared runtime imports used by Edge Functions must include their `.ts` extension, even when Vite accepts extensionless imports. A Supabase GitHub preview failure reporting only `failed to bundle function: exit status 1` can be investigated locally with `npx --yes deno check --config supabase/functions/deno.json supabase/functions/*/index.ts` (also run in CI). This checks all entrypoints without deploying; a successful check does not confirm hosted deployment.

## Wayback Snapshot Lookup

`WaybackLink` and `WaybackPage` share one action for saved AO3 works, shown in the story action menu and beside Date Updated in the details statistics. The action opens the authenticated `/wayback?url=…` route in a separate tab. This avoids async popup blocking and leaves the original library in place. The page invokes `wayback-lookup`, validates that a returned fixed snapshot still identifies the requested work, then replaces the lookup tab’s location. Failure or an unverified search shows a canonical work calendar link and Try Again. No story metadata, availability, notes, or reading history is written.

`server/ao3/wayback.ts` owns the resolver, content checks, and authenticated handler. It reuses `parseWorkUrl`, `waybackSnapshot`, `readBoundedBody`, and the existing metadata parser. Unlike metadata import, opening an adult-warning capture is allowed when its confirmation link identifies the requested work. A normal header login form does not invalidate a work page; login-only captures do. A warning page does not establish that its continuation or every chapter was captured.

The resolver queries Internet Archive’s [CDX API](https://github.com/internetarchive/wayback/tree/master/wayback-cdx-server) for the base work URL, adult-confirmed and entire-work variants (both combined query orders), plus the saved source/chapter/collection URL when distinct. Up to six exact index requests run two at a time, with five recent successful HTML records per response. An already saved fixed snapshot is also a verification candidate. Candidates are deduplicated and sorted newest first across variants. At most eight replay candidates are checked, with at most two archive-only redirects per candidate. Redirects must remain fixed captures of the same AO3 work; live AO3 and other hosts are never fetched. The 25-second overall budget includes six-second request timeouts, 100 KB index limits, and 4 MB HTML limits. Archive blocking or rate limiting stops further lookup calls; an incomplete lookup is reported separately from an empty index. Only public URLs are sent to Internet Archive, without organizer bearer tokens, AO3 credentials, or cookies.

The handler verifies the caller with Supabase Auth before retrieval. Each warm function instance coalesces identical pending URLs, permits two distinct concurrent lookups, and caches up to 100 completed results for ten minutes; archive-outage results are not cached. These are per-instance bounds, not a distributed rate limiter. Results are best effort among checked candidates, not a guarantee of the archive’s absolute latest usable page. The client limits its request to 30 seconds and offers the calendar even when the function is missing or the service is unavailable.

Deploy the new function alongside the frontend; no SQL migration is required:

```sh
supabase functions deploy wayback-lookup
```

`supabase/config.toml` disables gateway JWT verification for this function because the handler verifies every bearer token through Supabase Auth, matching the other user-facing functions and supporting modern signing keys. The function uses the platform-provided Supabase URL and service-role credential only to validate the caller; privileged credentials remain server-side. Unit tests cover identity, newest-first selection, adult warnings, login rejection, redirect isolation, bounds, caching, and authentication. Browser tests cover new-tab navigation and failure/calendar behavior on desktop and mobile using mocked archive results; they do not establish live Wayback availability.

## Server Boundary

`server/invite-user.mjs` is a trusted operator utility, never a frontend import. No browser-accessible endpoint can create accounts or mutate shared AO3 metadata. The authenticated `save_library_story` PostgreSQL function can create a bare shared work identity and atomically save only the caller’s private manual metadata and organization.

`supabase/functions/account-status/` establishes the authenticated Edge Function boundary. It verifies the supplied bearer token using `auth.getUser(token)`, derives identity exclusively from that verified user, restricts CORS to `APP_ORIGIN`, and returns only user ID and schema version with `Cache-Control: no-store`. The gateway JWT switch is off because the handler verifies tokens itself, including tokens using modern signing keys; it does **not** permit anonymous handler access. No privileged credential is required by this function.

To deploy it after project setup, set the **server-side** `APP_ORIGIN` secret in Supabase and run:

```sh
npx supabase functions deploy account-status
```

Supabase supplies its server URL and anon key. The function is optional for rendering the Phase 1 shell; future privileged operations must remain in trusted server code and must validate authorization for each operation. The Phase 3 importer runs in a separate trusted worker; email handlers remain future work. Phase 2 library writes use a narrow authenticated PostgreSQL RPC; the account-status function remains optional.

## Schema and Access Model

| Tables | Purpose and browser access |
| --- | --- |
| `works` | Globally unique AO3 identity and canonical metadata; readable only through your library |
| `authors`, `fandoms`, `tags` | Normalized shared AO3 metadata; readable only when linked to your saved works |
| `work_authors`, `work_fandoms`, `work_tags` | Many-to-many AO3 metadata relationships; same visibility rules |
| `library_entries` | Private status, progress, favorite, rating, notes, original URL, and manual overrides |
| `collections`, `collection_works` | Owned shelves and membership of owned library entries |
| `personal_tags`, `library_entry_tags` | Private organizational tags and owned entry membership |

The twelve foundation tables enable and force RLS; later migrations add the account-owned tables described in the project overview. Anonymous table access is denied. Personal rows require `auth.uid() = user_id` for both existing and new values. Composite foreign keys also prevent attaching another account's entry, collection, or tag. Shared metadata has no browser write grants; a trusted server can write it using a secret key.

`library_entries` creation is restricted to the authenticated save and restore functions. `save_library_story` is a narrowly scoped SECURITY DEFINER function with an empty search path. It validates an AO3 work URL, derives ownership from `auth.uid()`, creates or reuses the work identity, and saves private overrides and memberships in one transaction. It accepts no caller-supplied owner or work UUID. Existing owners may update a limited set of personal columns or delete their own entry. Work identity and original submission remain immutable on edits. Shared AO3 metadata has no browser write grants.

Deletion Undo requires `20261016000100_restore_library_story.sql`. Its narrowly scoped `restore_library_story` transaction verifies the authenticated owner and matching AO3 work URL, restores the private snapshot and surviving links atomically, and rejects conflicts. It does not grant direct INSERT access or modify shared metadata. Apply it through the migration workflow above; no hosted migration is applied automatically. Sample mode restores its browser-local snapshot without a database.

Key modeling decisions:

- `works.ao3_work_id` is globally unique; `(user_id, work_id)` is unique per library.
- `library_entries.original_url` preserves the exact user's submission, including chapter/query parameters. It is separate from `works.canonical_url`, which remains NULL until verified. The latter must match the canonical AO3 work ID and have a verification timestamp.
- `published_chapters`, `total_chapters`, and `is_complete` are nullable. Unknown totals stay NULL; zero is not a substitute for an unknown total. Progress defaults to zero fully read chapters.
- Reading status and AO3 completion are independent. No trigger changes personal progress or completion when shared metadata changes.

## Automatic Database Deployment

The existing [CI workflow](../.github/workflows/ci.yml) includes **Deploy Production Database**, which depends on both `checks` and `supabase`. | --- | --- |

| `SUPABASE_PROJECT_REF` | The production project reference from its Supabase Dashboard URL. |

Missing secrets fail the job with their names only. Enter values directly into GitHub’s secret settings; do not add them to source files. The CLI follows Supabase’s [GitHub Actions deployment guidance](https://supabase.com/docs/guides/deployment/managing-environments).

A separate environment named `Production – beyond-the-archives` does not replace it. Before consolidating environments, migrate required secrets and protection rules and explicitly update the workflow target; do not delete Production while this job still references it. Leave required-reviewer protection off for fully automatic deployment; if reviewers are configured, GitHub waits for their approval. Re-run a failed workflow from GitHub Actions after correcting its reported failure. Migration-history mismatches require operator review; the workflow does not reset the hosted database or repair migration history automatically.

This job deploys SQL migrations only. Frontend hosting, Edge Functions, worker scheduling, Supabase secrets/configuration, and companion releases retain their existing deployment procedures. A separately configured frontend auto-deployment is not gated by this database job. Use compatible schema changes or coordinate the frontend release when changes require the database migration first.
