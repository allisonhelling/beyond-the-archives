# Phase 1 UI Design System Audit

**Beyond the Archives and archives unfolded · November 19, 2026**

## Executive Summary

Both applications already share a visual foundation and several interaction primitives. The warm parchment palette, literary typography, square passive surfaces, compact filter controls, and collection artwork are deliberate design choices. The highest-priority findings are low contrast in the reader's dark theme for several default category colors in Colored Text mode and a 14 px mobile Bookshelf search field that falls below the existing 16 px iOS input convention. The audit sets a 13 px minimum for app UI text and 16 px for common reading and control roles. Across both apps, search bars should have no persistent focus styling applied to the field or its wrapper.

The main consolidation opportunity is the CSS around shared components. Dialogs, menus, filters, and tiles already have useful shared implementations, but app-level styles can assign them different measurements, state treatments, or color fallbacks. Address the shared sources first, using each app's established behavior to decide where a variant is warranted.

### Search Bar Focus

Remove any persistent focus ring, outline, shadow, border change, or background change driven by keyboard focus on a search field or its wrapper. This applies to all editable search bars in the organizer and reader, including primary and within-results search, tag and fandom search, searchable dropdowns, collection pickers, and Storage search. Preserve the native text caret and selection, normal search suggestions, keyboard navigation, and visible focus on separately actionable controls such as suggestion rows, dropdown triggers, and filter buttons.

Keyboard Tab reached the main Library and Bookshelf searches at 390 px with `:focus-visible` true. Both already rendered with the ordinary border color and no outline or shadow. The base styles in both apps suppress search outlines. Check the remaining search fields and their wrappers for inconsistent focus styling. W3C recognizes the insertion caret as a form of visible focus for text fields. Verify that keyboard users can still locate the focused field, including in forced-colors mode. [Organizer base styles](../src/styles.css#L33) · [Reader override](../reader/src/styles.css#L419) · [Shared dropdown search](../src/components/Dropdown.tsx#L64) · [WCAG 2.2 Focus Visible](https://www.w3.org/WAI/WCAG22/Understanding/focus-visible.html)

### Tag Appearance Contract

Both apps use the same six shape identifiers and the same renderer. The brief's Filled Chips is currently labelled **Borderless** and persists as `filled`. The other settings are Rounded Pill, Curved Rectangles, Sharp Rectangles, Text With Bullet Separators, and Text With Comma Separators. Organizer defaults to bullets and independent reader defaults to Borderless. Without an explicit text-color choice, Borderless uses Black Text and the others use Colored Text. Explicit choices persist across shapes.

The current category-backed renderer uses 7% and 16% tints in Colored Text and 15% and 21% in Black Text. Black Text maps to normal theme text, including light foreground in reader dark mode. Borderless starts with a transparent 1 px border and changes its color on hover or keyboard focus without resizing. Interactive tag text underlines in both states. Text-only options have no fill or border, and separators are separate spans. Removable chips, personal tags, and collection labels use the shared component's separate styling path. Audit them by role. Organizer account-backed text-color saves depend on the existing `20261117000100_tag_text_color.sql` migration. The reader implementation guide also describes older Borderless color behavior and an older category order. Reconcile that passage with current shared settings during a documentation change. ## Work Order After Review

1. **Phase 2** Apply the search-bar focus rule across both apps. Establish the 13 px UI minimum and 16 px text roles in shared typography tokens, then address mobile inputs and tag contrast through their existing component styles. Add spacing tokens where the first consumers need them.
2. **Phase 3** Align shared button and dialog styling, then review dropdowns, tooltips, tabs, filter controls, and feedback at their existing boundaries. Apply the shared text roles to those components and their compact variants. Keep app-specific layouts and operation semantics.
3. **Phase 4** Refine page-level alignment and terminology using the verified shared rules. Apply the typography sizes to branding, navigation, statistics, work information, and other page-specific text. Review the source-backed candidates against real data before changing them.

Exercise the documented connected flows, desktop/mobile states, keyboard navigation, actual iOS Safari, theme variants, long labels, layout persistence, and assistive technology. Tab through each search variant and check the field and its wrapper for persistent focus styling, verify the editing caret and search actions, and check visible focus on surrounding controls. Check computed type sizes against both text rules, including the smallest layouts, long labels, zoom, a customized tile layout, and all tag formats. Check for clipped chart labels, mobile navigation labels, and controls after text grows. Use the repository's existing Vitest and Playwright coverage for dialog, tooltip, display settings, responsive layouts, collection shelves, activity, reading display, and Storage.

## Audit Verification

The local Playwright/Chromium inspection used both sample servers. It captured desktop and mobile screenshots, inspected mobile Library, Bookshelf and reader prose, checked document overflow, and confirmed the current main-search focus styling and mobile field-size difference using real Tab input and computed styles. Contrast ratios use sRGB relative luminance for the stated foreground and background pairs. This is a sampled baseline. Screen-reader behavior, actual iOS focus zoom, connected sync, production behavior, and full WCAG conformance remain unverified.

- Organizer unit baseline passed **1,174 tests in 126 files**. The `test:unit` script includes the full organizer `src` and `server` test sets. The run emitted jsdom `window.scrollTo()` notices and exited successfully.
- Reader focused baseline passed **40 tests in three files** covering tile layouts, metadata filters, and the sample snapshot.
- Build, lint, database and connected browser suites were deferred to the implementation verification phases. The audit used local sample data and temporary screenshots. It changed no application source, behavior, or production state.
