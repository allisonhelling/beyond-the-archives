# Source Compatibility And Trust Boundaries

This is the historical Phase A inventory. The [Phase 0 baseline](../universal-stories/PHASE_0_BASELINE.md) records the current extension-only cutover, additive capability handshake, active boundaries and mixed-version behavior; older worker/version statements below describe the audited Phase A baseline.

Phase A preserves current formats, storage keys, permissions and runtime behavior. New contract vocabulary is [design notation](source-contracts.md), not additional fields accepted by old clients. Source-neutral compatibility changes belong to a separately reviewed later phase. Detailed backup procedures remain in [BACKUPS.md](../BACKUPS.md); reader operations remain in [reader implementation](../../reader/docs/IMPLEMENTATION.md).

## Rollback And Migration Constraints

A future source identity migration must retain work UUIDs and all private FKs, preserve null work IDs for deleted bookmarks, backfill every existing non-null AO3 identity into an explicit namespace, and enforce uniqueness in that namespace before admitting another source. Choose a column or relation model from the first provider's actual needs; Phase A does not mandate `work_sources`.

Readers must understand both legacy AO3 and new envelopes before new writers emit them. Old clients cannot safely display/save an unsupported source through an AO3-number payload. Additive rollout may gate new-source writes until all trusted mutation/backup/reader consumers are ready. Rollback after new-source rows exist must disable unsupported writes or use a tested down-conversion only for representable AO3 data; dropping identity/evidence fields loses meaning and is not a rollback strategy. Previously applied migration files remain immutable. Preserve safety copies, audit job history and authentication; do not “repair” identity by changing user-owned work associations silently.

No changes to grants, policies, device secrets, generated schema types, backup format versions or storage keys are part of Phase A. This matrix is a compatibility requirement for later changes, not proof that hypothetical v2 data already round-trips.
