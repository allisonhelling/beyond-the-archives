# Recovery And Staging Acceptance

## Approved Policy — 17 November 2026

The Application Owner owns this policy and approves production operations through a distinct, auditable gate. The designated infrastructure maintainer executes it. Production database and persistent user-owned Storage have **24-hour RTO and 24-hour RPO**. Retain daily points for **30 days**, weekly points for **12 weeks**, and monthly points for **12 months**. Encrypt transport and stored copies with AES-256 or an equivalent managed standard. Keep encryption keys and recovery credentials separately, restrict access and audit usage. Never commit credentials or expose them to application clients.

Conduct quarterly nonproduction drills and a drill before major schema, RLS or Auth changes. Verify database integrity, Storage bytes, account ownership and reader associations. Record recovery duration, maximum recoverable data age, failures and corrective actions. Production personal data must not enter ordinary staging/development. Production recovery requires separate authorization naming target, recovery point, operator and expected data loss. A merge grants no recovery authority. An unmet objective blocks rollout unless the Application Owner explicitly accepts it.

This supersedes the prior **undecided policy** wording in S1/S4. It approves policy and synthetic staging identities; it does not establish provider backup coverage, a scheduled independent backup destination or a successful provider disaster recovery drill.

## Real Staging Sessions

Use dedicated staging-only User A, User B and Admin accounts. Reuse an account only after verifying isolation and configuration. Use the genuine persistent staging Owner with MFA; never borrow a production identity/session or transfer ownership to a disposable fixture. Establish a missing staging Owner through the [controlled bootstrap ceremony](S2_APPLICATION_RBAC.md), with confirmed active account, enrolled TOTP, out-of-band UUID verification, request UUID and auditable operator reference. Preserve bootstrap/role/audit history indefinitely pending a separately approved audit retention policy. The backup retention policy does not authorize deleting live audit records.

`npm run test:privacy:staging` uses the existing `.env.staging.local` **public** profile and four short-lived access tokens supplied securely through process environment: `STAGING_USER_A_TOKEN`, `STAGING_USER_B_TOKEN`, `STAGING_ADMIN_TOKEN`, `STAGING_OWNER_TOKEN`. Do not put tokens in shell history, command arguments, source or chat. The Management API credential comes from `SUPABASE_STAGING_ACCESS_TOKEN` or the existing CLI keychain credential. No service key is needed by the runner. Admin and Owner must have completed real TOTP within the existing five-minute freshness window and retain audit-read permission. The runner does not enroll factors, refresh sessions or sign participants out.

Before writes, the runner verifies exact healthy staging project identity, four distinct GoTrue identities and live roles, one Owner, one retained successful bootstrap and anonymous denial. It appends normal redacted audit-read events, writes uniquely identified synthetic story/EPUB sentinels through owned APIs, tests own access and foreign/anonymous denial, and rejects direct role writes. Cleanup removes only IDs/paths generated by that invocation through normal owned APIs. Accounts, assignments and all audit events remain. Cleanup rechecks roles and aggregate history; metadata-only evidence is written under ignored `artifacts/privacy/`. This focused smoke complements the broader local S3 catalog/queue/browser matrix; it does not attest those additional surfaces.

## Large Restore Acceptance

`npm run perf:restore:staging` reuses the same verified sessions and existing 10,000-work performance generator. Set `STAGING_RESTORE_USER_ID` to the dedicated User A UUID through the secure operator environment. The runner requires that account's library/series/tags/jobs/history and saved-backup bucket prefix to be empty; do not run simultaneously with the privacy runner. No external backup input or target override is accepted. The fixture includes realistic summaries, notes, tags, collections and loaded series, generated in embedded PostgreSQL and bound only to the verified staging user.

The runner measures real HTTP export, preview and commit, plus compressed safety-copy upload through `save-backup` and download through Storage with SHA-256 equality. It runs empty and populated replacement restores, checks 10,000 restored private entries and visible identity/notes/status/overrides, then restores the initial empty library and removes its saved objects. It respects the existing one-minute cooldown, three-copy retention, safety-copy requirement and 60-second database budget. Shared public identity placeholders can remain; it never globally deletes shared works. Do not run alongside unrelated staging library traffic because current restore functions lock application tables.

If a request times out or fails, stop and inspect committed synthetic state; there is no automatic destructive retry or cleanup restore on an ambiguous outcome. A metadata-only report records the failed phase and completed timings under `artifacts/performance/`. Session expiry, missing backend/MFA or failed cleanup is a failure, never a successful benchmark. Passing requires all measured database phases below 60 seconds. An embedded result is a risk baseline and does not establish hosted HTTP acceptance. If reproduced on staging, profile the offending SQL and make a narrow forward fix, then rerun this same fixture; do not raise timeouts or bypass account restore authorization.

## Independent Recovery Bundle

`npm run recovery:bundle -- pack <plan.json> <new-directory>` encrypts explicitly supplied independent snapshot files with AES-256-GCM. `npm run recovery:bundle -- unpack <bundle-directory> <new-directory>` authenticates/decrypts them and checks each SHA-256 and length. Supply a unique random 32-byte base64 key as `RECOVERY_BUNDLE_KEY` from the separately audited secret manager. Never save that key with the bundle. No new dependencies, provider mutations, database/Storage restores, job changes or automatic deletion are performed.

The input plan has `version: 1`, `environment: "synthetic"` or `"production"`, `retentionClass: "daily"`, `"weekly"` or `"monthly"`, `consistencyReference`, `keyCustodyReference`, `operator`, `approvalReference`, and `assets`. Each asset requires `category`, an explicit local regular-file `path`, and actual source `capturedAt`. Every category below is required; multiple files per category are permitted. Recovery points older than 24 hours are rejected at packing; never substitute the packaging time for source capture time. Inputs must come from an approved consistent snapshot, not unrelated exports merely labeled with the same reference.

| Category | Required Contents And Recovery Verification |
|---|---|
| `database` | Schema, data, functions, grants, RLS, extensions, migration history, shared/private reader and organizer records; verify ordered history, constraints, private records and projection integrity |
| `auth-mfa` | Actual Auth UUIDs, users/identities, password/confirmation state, factors, required session metadata and encryption dependencies; verify fresh login, TOTP and recovery/re-enrollment policy without exporting seeds to logs |
| `roles-audit` | Assignments, role permissions and append-only audit, including original bootstrap; verify one active Owner, exact history and prohibition on account-export role injection |
| `storage-bytes` | Independent complete EPUB and saved-backup bytes; verify object counts, lengths and hashes, including large EPUBs |
| `storage-metadata` | Bucket policy/configuration, owned object manifest and associations, DB metadata; reconcile exact UUID prefixes and orphan/missing objects |
| `configuration` | Auth callbacks/hooks/templates, origins, frontend/Edge source and build hashes, runtime/dependency versions, bucket settings and disabled-by-default job configuration |
| `keys-credentials` | Restricted recovery export of required DB/Auth/Vault/provider/SMTP credentials and encryption root dependencies; the **bundle decryption key itself remains separate**; verify custodian access without printing values |

The encrypted manifest records source capture times, checksums, policy and retention expiry; plaintext outer files contain only cipher metadata. Bundle files and output directories use restrictive permissions and exclusive creation. Partial outputs lack a verified completion receipt and must not be used. `verified-files.json` explicitly reports `providerRecoveryExercised: false`; file decryption success cannot attest database/Auth/Storage restoration or production RTO. The synthetic test exercises all categories and random binary bytes, wrong-key refusal, corruption detection and overwrite protection.

Provider backup scope must be checked for the actual plan. [Supabase database backups](https://supabase.com/docs/guides/platform/backups) exclude Storage object bytes. A [project restore](https://supabase.com/docs/guides/platform/clone-project) has explicit configuration/object exclusions and encryption-root handling. Review the [current CLI recovery procedure](https://supabase.com/docs/guides/platform/migrating-within-supabase/backup-restore) against the installed CLI and source/target versions before choosing an export/restore path. A public-schema dump or account JSON is insufficient; do not assume Auth/MFA/root-key coverage from an artifact label.

## Capture, Retention And Secure Deletion Procedure

The maintainer must bind an independently owned encrypted destination, scheduler and secret-manager identity through the production operations gate before live capture. Capture at least daily, keep the last successful point while a new capture is incomplete, alert before the newest consistent database/object point exceeds 24 hours, and retain off-project immutable copies with access logs. Designate one daily point per week/month for weekly/monthly retention, or create separately encrypted points. Retain a promoted point until the longest applicable tier expires; never shorten retention by relabeling a point. Require captures plus transfer/verification to meet the 24-hour RPO, including during failures.

Review expired manifests and legal/incident holds without exposing contents. After approval through the operations gate, delete the expired point's unique decryption key and all wraps/escrow replicas from the separate key store, then delete every encrypted object version/replica and staging plaintext recovery workspace according to the storage provider's supported lifecycle. Record point ID, expiry, approval reference, key-destruction receipt and object-deletion receipts. Filesystem unlink alone is not secure erasure on SSDs/versioned services. Never remove a key shared by another retained point. Preserve independent audit receipts. This release implements expiry calculation, **not** a production scheduler or deletion executor.

1. Obtain an audited request with exact isolated destination, consistent recovery point, operator, maximum data loss and maintenance window. Do not start schedules/webhooks during recovery.
4. Restore independent Storage bytes and metadata through the supported Storage path; reconcile every manifest hash/count/length and owner prefix. Rebuild derived data through existing migrations/utilities. Reapply exact reviewed callbacks/hooks/origins, secrets and frontend/Edge artifacts; activate jobs only under their own approval.
5. Exercise real login, confirmation/recovery flow, TOTP, own-library reads/writes and foreign denials for User A/B/Admin/Owner and anonymous access. Verify reader cloud state, EPUB hashes, pairing associations and queue fencing. Use the local restore drill and staging fixtures as component checks; neither replaces this full ceremony.
6. Stop the clock only when those checks pass. Record total duration (including access, transfer and failures), oldest recovered data timestamp and age, all category checks, failures/corrections, operator, target and approval. RTO and RPO must each be at most 24 hours. Obtain explicit Owner risk acceptance for any unmet objective before rollout; no automated acceptance or invented default.
